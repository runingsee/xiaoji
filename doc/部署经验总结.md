# MiniLims 线上部署经验总结（2026-09 实测记录）

> 本文记录 MiniLims 首次上云部署（腾讯云 118.89.200.74）过程中踩过的坑、排查过程与最终解法，
> 供日后部署 / 维护 / 同类问题排查直接复用。
> 对应仓库分支：`feature/test3`；配套手册见《部署上云指南.md》。

## 0. 部署环境一句话概况

| 项 | 实际情况 |
|---|---|
| 服务器 | 腾讯云 118.89.200.74，2C2G（构建时明显吃紧） |
| 系统用户 | `ubuntu`（**非 root**，`/opt` 无写权限） |
| 管理通道 | 仅云控制台网页终端（VNC/OrcaTerm），**SSH 已移除**（此前被入侵） |
| Docker | client/server 均为 **28.1.1**（新版，对旧容器有兼容性影响，见 §4） |

| 数据库/缓存 | 复用宿主机已有 `mysql8`(:3306)、`redis`(:6379) 容器，`mini_lims` 库数据完好 |

以 `host.docker.internal` 访问宿主机 3306/6379，**不依赖公网回环**。

## 1. Git 通道：国内直连 GitHub 被墙 → SSH-over-443

**现象**：本地与服务器直连 `https://github.com` 报 `Empty reply from server`（443 TLS 被阻断），clone/pull/fetch 全部失败。

**根因**：国内网络对 GitHub https 直连不稳定；`ssh.github.com:443` 是 GitHub 官方备用 SSH 通道，443 端口不被墙。

**解法**：本地与服务器 `~/.ssh/config` 统一配置：

```bash
Host github.com
    HostName ssh.github.com
    Port 443
    User git
    IdentityFile ~/.ssh/id_ed25519_github   # 各机器自己的密钥
    IdentitiesOnly yes
```

remote 使用 `git@github.com:runingsee/MiniLims.git`，验证：`ssh -T git@github.com` 回显 `Hi runingsee!...`。

**经验**：凡是"国内服务器连 GitHub 失败、裸 https 不通"的场景，先试 SSH-over-443，改 config 即可，无需代理。

## 2. 服务器路径：非 root 用户不要用 /opt

**现象**：克隆/构建报 `Permission denied`。

**根因**：云服务器默认用户 `ubuntu` 对 `/opt`（root 属主）无写权限。

**解法**：项目放 `~/MiniLims`（即 `/home/ubuntu/MiniLims`）；后续 `sudo` 仅 docker 相关操作需要；
`ubuntu` 加入 docker 组（`sudo usermod -aG docker ubuntu` + 重新登录）后免 sudo 执行 docker 命令。

**经验**：部署文档中"路径用 `/opt`"只适用于 root 用户，非 root 一律用用户主目录。

## 3. 前端 web 镜像构建：两个连环坑

### 3.1 `COPY yarn.lock` 失败

**现象**：`docker compose build web` 报 `COPY yarn.lock: not found`。

**根因**：`MiniLims.Vue3/.gitignore` 中第 23 行把 `yarn.lock` 忽略了，文件从未入库 → 服务器 pull 后没有该文件。

**解法**（提交 `21a9ee7`）：
1. `git add -f MiniLims.Vue3/yarn.lock` 强制入库；
2. 从 `.gitignore` 移除该忽略行。

**经验**：Dockerfile 里 `COPY` 的文件，必须确认已在 git 仓库中（`git ls-files` 检查），
尤其要警惕 `.gitignore` 恰好忽略构建依赖文件。

### 3.2 前端构建 JS heap OOM

**现象**：Vben/Vite 构建中途 `JavaScript heap out of memory`（2G 内存服务器）。

**根因**：Vben Admin 前端工程大，默认 Node 堆内存（~2G）不够；2G 物理机构建时内存吃紧。

**解法**（提交 `0e2b592`）双管齐下：
1. Dockerfile 构建阶段加 `ENV NODE_OPTIONS=--max-old-space-size=2048`；
2. 服务器加 4G swap（`/swapfile` + `/etc/fstab` 持久化），物理内存不足时有兜底。

**经验**：小内存服务器构建 Vben 这类重前端，`NODE_OPTIONS` 与 swap 都要考虑；swap 命令：
`sudo fallocate -l 4G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile`，
并写入 fstab。

## 4. 数据库：旧 mysql8 容器与 Docker 28 不兼容 → 重建容器

**现象**：
- api 日志：`Couldn't connect to server DbType="MySql";ConfigId="0"`；
- api 容器反复 `Restarting (139)`；
- 直接 `docker exec mysql8 ...` 报诡异错误 `cannot exec in a stopped state: unknown`；
- 容器内看到 `connection refused (111)` 连宿主机/容器 IP 的 3306。

**根因**：`mysql8` 容器是 **2 周前**用旧版 Docker 创建的，Docker 升到 28.1.1 后，
该旧容器的网络转发 / exec 机制与新版不兼容（握手即断、执行报"stopped state"），
表现为"容器 Up 但服务实际不可达"。

**排查关键命令**：
```bash
docker ps                                   # mysql8 显示 Up（但实际异常）
docker exec mysql8 mysql -uroot -p -e "SELECT 1;"   # 反复失败/报错
docker logs --tail 20 mysql8                # 看内部真实日志
```

**解法**（按序，逐步升级清理强度）：
1. `docker restart mysql8` → 仍不稳；
2. 最终 `docker stop mysql8 && docker rm mysql8` **重建新容器**（保留数据卷 `/opt/mysql/data` 挂载），数据完好无损（`mini_lims`、`xiaoji` 库均在）；
3. 确认账号权限（`SELECT user,host FROM mysql.user`），保证 `root@'%'` / `minilims@'%'` 存在且有授权。

**经验**：
- Docker 大版本升级后，**旧容器建议主动重建**（`stop/rm/run`，卷不删），避免隐晦兼容问题；
- 容器重建**只要保留数据卷挂载**就不会丢数据，别慌；
- `mysql8`/`redis` 这类长期容器，重建前记录原 `docker run` 参数（本项目记在《记录文件.md》）。

## 5. 后端 api：启动流程未处理异常（连带 MySQL 连接）

**现象**：`Restarting (139)` + 日志中的 Unhandled exception 位于
`Program.cs → await app.UseAddTaskSchedulers()` → `TasksExtension.cs:line 37`（查询 `sys_tasks` 表）。

**根因**：启动时任务调度初始化要查数据库，**MySQL 连不上**（即 §4 的问题）导致未处理异常，进程直接崩。

**解法**：不单独改代码——先修好数据库连接（§4），api 随之后台任务初始化即可通过。

**经验**：`Restarting (139)` 优先看 `docker logs` 定位未处理异常；
"启动阶段查库失败"类问题，先确认数据库层，不要急着改业务代码。

## 6. 最大坑之一：Kestrel 只监听 localhost → nginx 502

> 本坑前后排查最久，现象极具迷惑性，务必牢记。

### 6.1 现象

- 浏览器 `http://118.89.200.74/` 页面能开（静态资源正常），但接口全部 502，前端提示"系统接口502异常"；
- nginx 日志：`connect() failed (111: Connection refused) ... http://172.19.0.2:8888/captchaImage`；
- 服务器 `curl http://127.0.0.1:8888/` 报 `Empty reply from server`；
- api 容器是 `Up` 状态，日志里 Elsa 后台任务（bookmark purge）还在正常跑。

### 6.2 排查路径（按序）

| 步骤 | 命令 | 结果解读 |
|---|---|---|
| 1. 容器内环境变量 | `docker exec minilims-api sh -c 'echo $ASPNETCORE_URLS'` | `http://+:8888` ✅ 存在 |
| 2. 容器内监听 | `docker exec minilims-api sh -c 'grep -i 22B8 /proc/net/tcp*'` | `0100007F:22B8` = **127.0.0.1:8888** ⚠️ |
| 3. 容器 IP | `docker inspect minilims-api --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}}={{$v.IPAddress}} {{end}}'` | `minilims_default=172.19.0.2` |
| 4. web→api 链路 | `docker exec minilims-web sh -c 'wget -qO- http://api:8888/'` | 被拒（web 容器内 8888 连不上） |

> 说明：容器是无 `ss`/`ps` 的精简镜像，改用 `/proc/net/tcp`（8888 十进制 = **22B8** 十六进制）。

### 6.3 根因

`AMiniLims/MiniLims.Admin.WebApi/appsettings.json` 中 `"urls": "http://localhost:8888"`，
被 Furion 配置加载链以**配置文件为准**，导致**容器环境变量 `ASPNETCORE_URLS=http://+:8888` 未生效**——
Kestrel 最终只绑定了容器内回环 `127.0.0.1:8888`（/proc/net/tcp 可见 `0100007F:22B8`）。

于是：
- nginx（web 容器）访问 api 容器 IP `172.19.0.2:8888` → 回环外不可达 → **111 refused**；
- 宿主机 `curl 127.0.0.1:8888` 走 docker-proxy 转发到容器 IP → 转发落空 → **Empty reply**。

两个症状指向同一个根因：**Kestrel 没绑 `0.0.0.0`**。

### 6.4 解法（提交 `40e4061`）

```json
"urls": "http://0.0.0.0:8888",
```

### 6.5 验证（确认 0.0.0.0 生效）

```bash
docker exec minilims-api sh -c 'cat /proc/net/tcp /proc/net/tcp6 | grep -iE "22B8"'
# 应出现：00000000:22B8  → 0.0.0.0:8888 LISTEN ✅
curl -i http://127.0.0.1:8888/         # 200 OK，Kestrel 头 ✅
docker exec minilims-web sh -c 'wget -qO- --timeout=5 http://api:8888/ | head -c 300'   # 页面内容 ✅
```

### 6.6 经验与预防

- **现象辨识**：`Empty reply from server`（宿主 curl）+ `Connection refused`（nginx 日志）同时出现
  ≈ Kestrel 没绑对外接口，别先怀疑网络/防火墙。
- **容器内看监听**：精简镜像没有 `ss`/`netstat`/`ps` 时，用 `/proc/net/tcp`（IPv4）与 `/proc/net/tcp6`；
  8888 对应十六进制 `22B8`，`0A` 状态即 LISTEN；`0100007F` = 127.0.0.1，`00000000` = 0.0.0.0。
- **环境变量可能被框架覆盖**：容器内环境变量"存在"≠"生效"；Furion/配置文件优先的场景，
  **直接改 `appsettings.json` 的 `urls` 为 `0.0.0.0`** 是可靠做法（本地 `localhost:8888` 访问不受影响）。
- **nginx 用服务名反代**（`proxy_pass http://api:8888/`）在容器重建后 IP 变化时需注意
  重新解析（`/etc/hosts` 静态写入，rebuild web 容器刷新），本次 IP 恰好未变。

## 7. 排查工具箱（服务器终端速查）

```bash
# 容器内看监听端口（无 ss/netstat 环境）：8888 → 22B8
docker exec minilims-api sh -c 'cat /proc/net/tcp /proc/net/tcp6 | grep -iE "22B8"'

# 容器内看环境变量是否真的注入
docker exec minilims-api sh -c 'echo URLS=$ASPNETCORE_URLS'

# 容器当前 IP / 所在网络
docker inspect minilims-api --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}}={{$v.IPAddress}} {{end}}'

# web 容器解析 api 服务名得到的地址（nginx 实际连的）
docker exec minilims-web cat /etc/hosts | grep -i api

# 从 web 容器直连 api 服务名（验证反代链路）
docker exec minilims-web sh -c 'wget -qO- --timeout=5 http://api:8888/ | head -c 300'

# 后端日志关键帧
docker logs --tail 50 minilims-api
docker logs minilims-api 2>&1 | grep -iE "listening|started|error|exception|fail" | head -40

# nginx 错误日志（看 upstream 连的 IP 和端口）
docker logs --tail 20 minilims-web
```
