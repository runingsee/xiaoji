# 想法记录与分析技能

当用户提出新的产品想法时，自动将想法记录到项目文档中，并生成完整的分析报告和解决方案。

## 触发条件

- 用户说"记一个想法"、"记录想法"、"记想法"
- 用户说"new idea"、"add idea"、"new thought"
- 用户说"我想到了"、"有个想法"、"关于XX我有个主意"
- 用户提出新的功能建议、设计思路、或对现有方案的修改意见

## 工作流程

### Step 1: 读取上下文

读取以下文件获取当前项目上下文（如果文件不存在则跳过）：
- `项目说明.md` — 产品定位、目标用户、核心场景
- `技术方案.md` — 当前技术架构、数据模型、API 设计
- `品牌方案.md` — 品牌定位、视觉方向
- `myidea/myidea.md` — 已有的想法列表（了解已有讨论，避免重复）
- `dev-design/` 目录 — 开发设计文档（了解技术细节）

### Step 2: 提取用户想法

从用户消息中提取：
1. **想法描述**：用户的原始表述（优化表达，但不改变原意）
2. **想法编号**：自动递增（查看 myidea.md 中已有的最大编号 + 1）
3. **分类**：属于产品设计、技术架构、交互体验、商业化、还是其他

### Step 3: 写入 myidea/myidea.md

将想法追加到 `myidea/myidea.md` 文件末尾，格式：

```markdown
### 想法N：{简短标题}
- 描述：{优化后的详细描述，包含背景、具体场景、用户价值}
- 分析结果：{对照当前设计方案的差异分析，覆盖度评估}
- 解决方案：{具体的实现路径、优先级建议、分阶段计划}
```

要求：
- 想法描述要清晰完整，包含"为什么做"和"怎么做"
- 分析结果要对照当前技术方案，指出覆盖或未覆盖的部分
- 解决方案要具体可执行，包含优先级（V1/V2/V3）

### Step 4: 写入 myidea/myidea-analysis.md

在 `myidea/myidea-analysis.md` 中追加完整的分析章节，格式：

```markdown
## 想法N：{标题}

### 优化描述
> {完整的优化后描述}

### 对照当前设计
| 维度 | 当前设计 | 想法要求 | 差异/覆盖 |
|------|---------|---------|-----------|
| ... | ... | ... | ... |

### 分析结果
1. {核心价值分析}
2. {与现有设计的关系}
3. {潜在风险}
4. {可行性评估}

### 解决方案
| 阶段 | 策略 | 说明 |
|------|------|------|
| V1 | ... | ... |
| V2 | ... | ... |
```

### Step 5: 更新总览表

在 `myidea/myidea-analysis.md` 的"想法总览"表格中追加新行，并更新"演进路径"部分。

### Step 6: 反馈总结

完成后向用户总结：
1. 想法编号和标题
2. 核心结论（是否需要改动现有设计）
3. 建议的优先级（V1/V2/V3）
4. 是否有矛盾或需要注意的地方

## 格式规范

### myidea.md 中的想法格式
- 以 `### 想法N：` 开头，N 递增
- 使用 `- 描述：`、`- 分析结果：`、`- 解决方案：` 三个固定字段
- 想法编号连续，不跳过（即使想法被标记为"已完成"）

### myidea-analysis.md 中的分析格式
- 以 `## 想法N：{标题}` 开头
- 必须包含四个子章节：优化描述、对照当前设计、分析结果、解决方案
- 使用 Markdown 表格进行对照分析
- 末尾更新总览表和演进路径

## 注意事项

1. **不修改已有想法**：只追加新想法，不改动已有内容
2. **编号自动递增**：读取 myidea.md 中最大编号 + 1
3. **优化表达但不改变原意**：提升文字的清晰度和结构性，保留用户的原始意图
4. **对照当前设计**：分析必须基于 `技术方案.md` 和 `dev-design/` 中的实际内容
5. **解决方案要分层**：明确 V1（当前阶段）、V2（后续）、V3（远期）的处理方式
6. **商业考量**：涉及商业化的想法需提醒用户考虑付费意愿和商业模式
7. **技术可行性**：涉及技术实现的需对照当前技术栈（.NET Core + MySQL + Vue3 + Vant + DeepSeek）
